# Contributing

Thanks for your interest in contributing. This page covers setup, conventions,
and the release checklist.

## Development setup

Requires [uv](https://docs.astral.sh/uv/) and Python 3.10–3.14.

```powershell
uv sync --extra pyside6 --group test
$env:QT_QPA_PLATFORM = "offscreen"
pytest -v
```

On macOS/Linux use `export QT_QPA_PLATFORM=offscreen` instead. The test suite
runs fully offscreen — no desktop session needed.

### Other Qt bindings

The library runs on PySide6, PyQt6, PyQt5 and PySide2. The extras are mutually
exclusive, so test another binding in a throwaway environment instead of
switching your `.venv`:

```bash
uv run --isolated --extra pyqt6 --group test pytest -v        # tests
uv run --isolated --extra pyqt6 examples/smil_showcase.py     # an example
# --extra pyqt5, or: --python 3.10 --extra pyside2  (PySide2 has no wheels past 3.10)
```

Day to day, PySide6 is enough. Also run the other bindings when you touch
`_qt.py`, `rendering/engine.py`, HiDPI/DPI handling, or event/theme handling,
and all of them before a release. To force a binding when several are installed
in one environment, set `PYSIDE_ICONIFY_QT_API` (and `PYTEST_QT_API` for
pytest-qt) to the same value.

`examples/` imports Qt through `examples/_qt.py` so each example runs on every
binding; example code is not meant to be copied verbatim, the README quick start
is.

Rules that keep the multi-binding support working:

- **Import Qt only through `pyside_iconify._qt`.** Never write
  `from PySide6 ...` inside `src/`; `_qt.py` is the single place that picks a
  binding. Tests do the same through `tests/qt.py`. `core/` still imports no Qt.
- **Qt differences go into `_qt.py` or a small guarded helper**, with a comment
  naming the binding/version that needs it (for example `ThemeChange`
  missing in PyQt, `scaledPixmap` size semantics before Qt 6.8).
- A new Qt class used in `src/` must be added to the matching name list in
  `_qt.py`; then run `python tools/gen_qt_stubs.py` to regenerate the stubs.

## Project layout

See [docs/architecture.md](docs/architecture.md) for the layering rules
(`widgets/ → rendering/ → core/`, no Qt in `core/`) and the reasoning behind
each directory. The short version of "where does my change go":

| Change touches                                 | Directory       |
| ---------------------------------------------- | --------------- |
| Icon names, JSON parsing, colors, sizes        | `core/`         |
| QIcon/QPixmap rendering, caching, placeholders | `rendering/`    |
| `IconWidget`, QSS, animation                   | `widgets/`      |
| Downloads, disk cache                          | `network/`      |
| Putting icons on existing widgets              | `integrations/` |
| Public API surface, global config              | package root    |

## Conventions

- **Type hints everywhere**; the package ships `py.typed`.
  No bare `Any` in public signatures.
- **Errors are loud.** Unparseable input raises a specific exception
  (`InvalidColorError`, `InvalidSizeError`, …) — never a silent fallback.
- **Defaults are side-effect free.** Visual effects (hover, selection) are
  explicit opt-in via parameters.
- **Platform behavior is verified with probes before being designed against**
  (offscreen platforms can differ from real ones; measure, then design).
- **Keep `__init__.pyi` in sync.** Signatures in `src/pyside_iconify/__init__.pyi`
  are written by hand; after changing a public signature, update the stub, then
  run `python tools/sync_pyi_docs.py` to copy docstrings into it (editors show
  them on hover). `--check` reports drift without writing.
- **Keep the type stubs per binding in sync.** `src/pyside_iconify/_qt.pyi` and
  the packages under `stubs/` are generated by `python tools/gen_qt_stubs.py`
  (run `sync_pyi_docs.py` first, because the stub packages copy
  `__init__.pyi`). CI runs `--check`; do not edit those files by hand.
- Comments stay minimal — what/why, no debugging history.
- No emoji in code, docs, or commit messages.

## Testing expectations

- Every bug fix ships with a regression test that fails without the fix.
- Rendering changes: assert actual pixels (`pixmap.toImage().pixelColor(...)`)
  or rendered output, not just that "no exception occurred".
- Remember `update()` is an asynchronous repaint request — call `grab()` to
  force synchronous rendering before asserting on cache keys or pixels.
- Performance-relevant changes: run `uv run benchmarks/list_scroll.py`
  before and after, and quote both numbers in the PR.

## Translations

The README ships in several languages under `docs/readme/`. English
(`README.md`) is the source of truth; fixes to translations are welcome and
are among the easiest first contributions.

## Release checklist

Maintainers only. All build/publish commands are run by a maintainer.

1. Run the full suite: `pytest -v` (all green, including
   `tests/test_render_cache.py`).
2. Long-run memory soak: `uv run benchmarks/memory_soak.py` for at least
   30 minutes; RSS must not grow without bound.
3. Build: `uv build` — then audit the artifacts:
    - no `__pycache__`, `.pytest_cache`, `.workbuddy`, or temp files inside
    - no secrets, tokens, or local paths
    - `py.typed` and `_qt.pyi` present in the wheel
    - `LICENSE` and README present in the sdist
4. Bump `__version__` in `src/pyside_iconify/__init__.py` **and** the pins in
   the `pyqt6` / `pyqt5` / `pyside2` extras of `pyproject.toml`
   (`pyside-iconify-stubs-<binding>==<version>`), run
   `python tools/gen_qt_stubs.py` (it rewrites the stub packages' version),
   then `uv lock`, commit and push. `python tools/gen_qt_stubs.py --check`
   fails if any of these are out of step.
5. Tag and push the tag; the publish workflow does the rest (run the full CI
   as a gate, build, wait for approval of each package's environment, upload
   to PyPI, then create the GitHub Release with generated notes):

    ```bash
    git tag v1.2.0
    git push origin v1.2.0
    ```

   The tag must equal `v` + `__version__`, otherwise the build job fails.
   To rehearse on TestPyPI, run the "Publish to PyPI" workflow manually and
   choose `testpypi`.

Four PyPI projects are released from the same tag: `pyside-iconify` and the
type-stub packages `pyside-iconify-stubs-pyqt6`, `-pyqt5` and `-pyside2`. The
workflow uploads the stub packages first and the library last, because the
library's extras pin the stubs at the same version. If a release fails after the
stubs were uploaded, those versions are taken; bump the version and release
again.

One-time setup, before the first release that includes the stubs:

- On PyPI (and TestPyPI, if you rehearse there), add a Trusted Publisher for
  each of the four projects. PyPI refuses two *pending* publishers with the same
  repository, workflow and environment, so each package has its own environment
  name: `pypi-release` for the library and `pypi-release-pyqt6`,
  `pypi-release-pyqt5`, `pypi-release-pyside2` for the stubs (`testpypi-release*`
  on TestPyPI). The full table is in the header of
  `.github/workflows/publish.yml`.
- In the GitHub repository settings, create the same environments. Adding
  "Required reviewers" to them makes every upload wait for a manual approval.
